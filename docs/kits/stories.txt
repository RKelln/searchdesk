# The feature contract

This file is all you need to write a Search Desk feature. A feature is one file that follows the rules below. If it
follows them, it cannot break the rest of the app, and the app's self-test can check it.

Search Desk is a job-search helper that runs in a browser with no install and no server. There are no packages, no
frameworks and no build step. Every file is a plain script.

## 1. A feature is one file

```js
// features/sites.js
Desk.register({
  id: 'sites',                       // matches the file name; lowercase, a-z and hyphens
  name: 'Job sites',                 // plain words, shown to people
  purpose: 'Keep the job sites you use in one place.',
  types: ['site'],                   // record types this feature owns (may be empty)
  uses: ['calendar'],                // optional: other features it adds a nicety to when present
  strings: { addSite: 'Add a site', /* ... */ },
  css: `.sites-list { /* ... */ }`,
  logic: {                           // pure functions only: no DOM, no Desk globals, no time or random
    sortSites(sites) { /* ... */ },
  },
  mount(ctx) {                       // called once at start; register slots here
    ctx.slot('tab', { id: 'sites', label: ctx.t('tabLabel'), render: (el) => { /* ... */ } });
  },
});
```

The file does nothing at load time except call `Desk.register`. Nothing touches the DOM until `mount` runs. That is
what lets the check runner load the file with no page, and test `logic`.

To add a feature: put the file in `features/`, add its id to `Desk.features` in `features/list.js`, and write
`checks/<id>.check.js`. If the id is also in `Desk.planned` (ideas not built yet), delete that line, so the feature is
not listed twice.

## 2. What `ctx` gives a feature

`mount(ctx)` receives `ctx`. It is the only way a feature talks to the app. The shell calls it as `def.mount(ctx)`, so inside `mount`, `this` is your registered object and `this.logic` is your `logic` (the example uses this). Undo belongs to the shell: `ctx.store` has no `undo`.

| `ctx.` | What it does |
|---|---|
| `store.all(type)` / `store.get(id)` | read records; deleted ones are hidden unless you pass `{withDeleted: true}` |
| `store.put(record)` | create or update a record of a type you own; sets `id` (if missing), `updated`, and `source` (default `user`) |
| `store.remove(id)` | mark one of your records as deleted |
| `store.ext(id, patch)` | set this feature's `ext.<id>` on any record. On `'settings'` it works even if that record does not exist yet (core makes it) |
| `store.batch(label, fn)` | group writes into one undo step |
| `slot(name, def)` | add UI at a named place (section 3) |
| `h(tag, attrs, ...children)` | build elements safely (section 4) |
| `t(key, vars)` | this feature's strings, then the core strings; `{name}` in a string is replaced from `vars` |
| `ui.toast(text, {undo})`, `ui.confirm(text, {yes, no}?)`, `ui.go(tab)` | small interface helpers. `ui.toast` with `{undo: true}` shows an Undo button for 10 seconds; it goes away if a newer change is made. `ui.confirm` asks a yes/no question and returns a Promise that resolves to `true` or `false`; `yes` and `no` are optional button words. |
| `renderSlot(name, el, ...args)` | show the entries other features put in a slot (for example `ctx.renderSlot('job.panel', el, job)`); each gets its own empty block, an empty one is left out, and one that fails shows a short plain line instead. Buttons for `job.actions` and `event.actions` are made for you (test name `action-<id>`). Returns how many entries it showed, so you can write "Nothing here" when it is 0 |
| `route()` | the current screen and its parts, from the address: `#jobs/j_abc/edit` gives `{tab: 'jobs', args: ['j_abc', 'edit']}`; change it with `ui.go('jobs/j_abc')` |
| `fmt.date(v)`, `fmt.time(v)`, `fmt.dateTime(v)`, `fmt.relative(v, now)`, `fmt.daysFrom(v, now)` | show dates in plain words ("Thu Oct 22", "6:30pm", "in 3 days", "2 days late"); `v` is `YYYY-MM-DD`, `YYYY-MM-DDTHH:MM` or an ISO time |
| `has(featureId)` | whether another feature is loaded, for soft `uses` |
| `locale` | the locale pack (local help, sites, rules), read-only |
| `now()` | the current time as a Date (tests can fix it). For a `YYYY-MM-DD` day key, pass it to `ctx.fmt` or convert it; it has no `slice` |
| `profile()` | the profile record |
| `profileLines(profile?)` | the profile lines an AI question will contain: only fields whose "send to AI" switch is on (the same function the recipes use) |
| `backupNudge()` | whether to remind the person to save a copy: `{show, text, days}` (`show` is true when there are changes since the last export and either 7 days have passed or there are 10 or more records; `days` is null if never exported). Used by Home |
| `wide()` | true when the window is wide enough for the layout kit's two-pane and dashboard layouts (1100px, the same number as the `min-width: 1100px` rules in `core/desk.css`). Use it to choose a different default on a big screen — a board instead of a list, say — while a phone keeps the simpler one. The screen is drawn again when this flips, so a person who drags the window narrower or wider gets the right layout without tapping anything. |
| `pref(spec)` / `pref(key)` / `pref.set(key, value)` / `pref.note(text)` | a preference, saved and drawn for you (section 3) |
| `events.current()` / `events.refresh(opts?)` | the events to show: `{events, source, generated, note}` where `events` are `{id, title, start, end, venue, address, url, tier, tags}`, `source` is `'cache'` or `'snapshot'`. `current()` is instant. `refresh()` returns a Promise and asks `core/net.js` to fetch the latest only when live events are on (otherwise it just resolves `current()`); the screen is drawn again after a good fetch. `note` is a plain line when a fetch failed. Used by Events |
| `download(name, text, type)` | save a text file (for example a calendar `.ics`). `name` uses only letters, digits, `-`, `.`, `_` (up to 80 characters); `type` is `text/calendar`, `text/plain`, `text/csv` or `application/json`. Returns `true`, or `false` if refused |
| `recipe(def)` | register an AI recipe (the same id again replaces it) |
| `removeRecipe(id)` | take back a recipe this feature registered (for example a task the person deleted) |

Records are plain objects. Every record has `id`, `type`, `updated`, `source` (`user`, `ai`, `example`, `feed` or
`import`), and sometimes `deleted: true` and `ext`. Unknown types and unknown `ext` keys are kept and exported
untouched, so never delete what you do not own.

## 3. Slots

| Slot | Where it shows | `def` |
|---|---|---|
| `tab` | a screen in the main menu | `{id, label, order?, render(el)}` |
| `home` | a block on Home, under "Today" | `{id, order?, render(el)}`; render nothing to hide it |
| `job.panel` | a section in a job's detail view | `{id, title, render(el, job)}` |
| `job.actions` | a button on a job's detail view | `{id, label, run(job)}` |
| `event.actions` | a button on an event row | `{id, label, run(event)}` |
| `settings` | a block on the Data and settings screen | `{id, title, render(el)}` |
| `print` | a section in the printable summary (if `print` is loaded) | `{id, title, render(el)}` |
| `ai` | a block on the AI screen, between the task list and the open task | `{id, title?, render(el, {selected, args}), paste?(text)}`; `selected` is the open task's recipe or null. `paste(text)` may read pasted text that is not an AI answer: return `null`, or `{text, render?(el)}` to show a result |

Every slot entry needs an `id`. A `label` or `title` is the words people see, from your strings (`ctx.t('...')`).

**The screen is drawn again after every store change**, so anything kept inside `render` (half-typed text, an open
form) is lost. Keep that state in variables inside `mount`, and call `ctx.ui.go('<your tab id>')` to draw again. To
change a record you own (for example a suggestion's `status`), `put` the whole record:
`ctx.store.put(Object.assign({}, ctx.store.get(id), { status: 'taken' }))`. `ctx.locale` is frozen; read it only.
Add the `data-test` names your tests use to `tests/e2e/README.md`.

New slots are added to core, never improvised inside a feature. If a feature needs a slot that is not here, stop and
say so.

### Remembering a setting

A person turning something on expects it to still be on tomorrow. There is one way to do that, and one way that looks
like it works and then fails the self-test.

**Use `ctx.store.ext('settings', patch)`.** Never `localStorage`: it is a banned word, the self-test scans for it and
fails the feature, and it is not where the backup is made from.

```js
// in mount
ctx.slot('settings', { id: 'mine', title: ctx.t('settingsTitle'), render: renderSettings });

function renderSettings(el) {
  const s = ctx.store.get('settings') || {};        // undefined until something is saved
  const size = (s.ext && s.ext.mine && s.ext.mine.size) || 'normal';
  el.appendChild(h('p', { class: 'muted' }, ctx.t('sizeLabel') + ': ' + size));
}
```

Five things to know:

1. **Where it goes.** Your patch lands on the `settings` record under `ext.<your feature id>`, so two features can
   both have a `size` without colliding. Read it back from `ctx.store.get('settings')`.
2. **It merges.** `ext` copies the keys in one at a time, so saving one setting does not wipe another. You never need
   to read-modify-write the whole object to add a key.
3. **The record may not exist yet.** On the first save, core makes it. Nothing is counted as a change to back up, and
   `ctx.store.get('settings')` returns `undefined` until then, so always guard the read.
4. **It travels in the backup.** The `settings` record goes out in the person's file and comes back on another device.
   Only core's own `lastExport`, `exampleLoaded` and `inboxSeen` stay on the device. So a setting is not "remembered on
   this device" unless you say so in your own words.
5. **Treat an unknown value as your default.** A file can be old, hand-edited, or from a version that offered different
   choices. If the saved value is not one you offer, show your default and do not crash. Write this check in `logic`
   and test it.

To change it, write and redraw: `ctx.store.ext('settings', { size: v }); ctx.ui.go('data');`. Saving is a store change,
so it lands on the undo stack, but nothing pops up on its own — if you want an Undo button for it, pass one:
`ctx.ui.toast(ctx.t('saved'), { undo: true })`.

There is a `settings` slot on the Data screen for exactly this. No feature uses it yet, so the block you add is the
first one there.

### A preference: `ctx.pref`

Hand-rolling a preference is the one thing a feature used to do badly, so core does it. Say what the preference *is*,
and you get a labelled control, saved, checked against your own list, and put on the Data screen.

```js
ctx.pref({ key: 'size', type: 'choice', label: 'Text size', def: 'normal',
           options: [{ value: 'normal', label: 'Normal' }, { value: 'big', label: 'Bigger' }] });
ctx.pref({ key: 'contrast', type: 'toggle', label: 'Stronger contrast', def: false, onChange: apply });
ctx.pref.note('These settings are saved in your backup file.');
```

| | |
|---|---|
| `key` | `ext.<feature id>.<key>` on the `settings` record. Lowercase, then letters or digits: `size`, `lateDays`. Two features can both have a `size`. |
| `type` | `'choice'` (a list of options) or `'toggle'` (on or off). Those two are all there is; a new kind is added to core, never improvised. |
| `label`, `options[].label` | the words a person reads, so from your strings (`ctx.t`). Grade 6. |
| `def` | the value before anyone chooses, and the value a stale save falls back to. For a `choice` it must be one of your options; core says so if it is not. |
| `onChange(value)` | runs **after** the choice is saved, so it can read the new one. For a preference that changes the page — a class on `document.documentElement`. Saving is already done; do not save again. |
| `hint` | a short line under this one row. `pref.note(text)` puts one line under the whole block. |

Reading and writing:

```js
ctx.pref('size')                  // 'big' -- the saved value, or def if the saved one is not offered
ctx.pref.set('size', 'bigger')    // true, or false if 'bigger' is not one of your options (nothing is saved)
```

Five things worth knowing:

1. **You write no CSS.** The controls are styled in `core/desk.css`, in light and dark, and the row sits side by side
   when there is room and stacks when there is not.
2. **A stale value is never your problem.** If the saved value is not one you offer — an old file, or one edited by
   hand — reading gives you `def`. The control shows the default rather than a blank option.
3. **All of one feature's preferences land in one block**, titled with the feature's own `name`. A feature with no
   preferences adds no block at all.
4. **`data-test` names are made for you:** `pref-<key>` on the control and `pref-reset-<key>` on the way back. Add
   them to `tests/e2e/README.md` if you test them.
5. **A "Start again" link appears** on a row that is not at its default, and puts the default back. Nothing appears
   while there is nowhere to go back from.

The parts that decide what a saved value means are `Desk.prefs.allowed(def, value)` and `Desk.prefs.read(def, ext)`,
pure, and checked in `tests/unit/prefs.test.js`. So a feature that uses `ctx.pref` has less `logic` to test, not more.

## 4. `h()`: the only way to make elements

- Children that are strings become text nodes. There is no way to pass HTML.
- `href` must be `https:`, `http:`, `mailto:` or `tel:` (a phone number: digits, `+`, `-`, spaces, brackets); anything else is dropped. Links get `rel="noopener noreferrer"` and
  open in a new tab.
- `on: { click: fn }` attaches handlers. `class`, `aria-*`, `data-*` and form attributes pass through.
- On a `<select>`, `value` picks the option to show, so a control can show what the person chose. `<option value>` is
  the attribute it always was. If the value matches no option — a saved choice that has gone stale — the select shows
  its first option rather than a blank control.

```js
h('a', { href: job.link }, 'Open the posting')
h('button', { type: 'button', on: { click: save } }, ctx.t('save'))
```

`click` is not special. Any event name goes through, so a feature can use `focus`, `blur`, `change`, `input`,
`keydown`, `pointerdown`, or a drag (`dragstart`, `dragover`, `drop`). Handlers only ever arrive through `on`:
`ondragstart="..."` as an attribute is dropped.

```js
// Drag a card onto another one. This needs no permission and no core change.
const card = h('div', { class: 'card', draggable: 'true', on: {
  dragstart: (e) => e.dataTransfer.setData('text/plain', job.id)
} }, job.title);

const lane = h('div', { class: 'lane', on: {
  dragover: (e) => e.preventDefault(),   // without this the drop never fires
  drop: (e) => { e.preventDefault(); move(e.dataTransfer.getData('text/plain')); }
} });
```

Two things that bite: `dragover` must call `preventDefault()` or the browser refuses the drop, and the data has to
travel through `dataTransfer`, because a drag is not a normal event and the handler gets no arguments to close over.

### Looking like the rest

Plain buttons, inputs, `details` and headings are already styled, in light and dark, so a feature with no CSS looks
right. When you do write `css`, use the colours from `core/desk.css` instead of your own: `var(--surface)`,
`var(--surface-2)`, `var(--text)`, `var(--muted)`, `var(--line)`, `var(--accent)`, `var(--accent-soft)`,
`var(--danger)`, `var(--danger-soft)`, `var(--warn)`, `var(--warn-soft)`, `var(--warn-edge)`, `var(--radius)`, `var(--shadow)`. Then dark
mode works by itself. Shared classes: `card` (a white box with a border), `chip` (a small rounded label), `muted`
(grey text), `sr-only` (read aloud but not shown). `class: 'primary'` makes the main button on a screen; a button with
`aria-pressed="true"` shows as picked. To see your feature on a phone and a computer, in light and dark, run
`uv run tools/screens.py --only <screen>` and open `screens/index.html`.

**If your feature changes one of those variables**, so a person can make the page stronger or larger, then dark mode
is your problem too — and here is the whole of what you need to know. Dark mode follows the device, through
`prefers-color-scheme` in `core/desk.css`. **There is no `.dark` class and no `data-theme` attribute** — do not invent
one, and do not write rules for one. Put the change under a class of your own on the page, and give the dark values in
a media query:

```css
html.mine-bigger { font-size: 140%; }
html.mine-contrast { --muted: #505050; }
@media (prefers-color-scheme: dark) {
  html.mine-contrast { --muted: #c5cbd3; }   /* the same rule, with dark values */
}
```

One class on `document.documentElement` (`classList` and `document` are not banned words) and one media query is the
whole job. Check the numbers if you can: WCAG AA wants 4.5:1 against the page background for body text and 3:1 for a
line or a border, and the app's own defaults do not always reach that, which is usually why the setting exists.

### The layout kit: a desktop layout with no CSS of your own

A feature does not have to invent a layout for a big screen. These class names are all the app has, and they are
what make a screen look right on a computer as well as a phone. **On a phone every one of them is a single column**,
so using them costs nothing there and they cannot break a phone layout.

| Class | What it gives you |
|---|---|
| `cols` | a list of cards that spreads into as many columns as fit, each at least 20rem wide |
| `cols cols-sm` | smaller cards (16rem), so a wide screen fits more of them — good for short cards |
| `cols cols-lg` | bigger cards (26rem), for cards with paragraphs in them |
| `split` | two panes side by side on a wide screen, one above the other on a phone |
| `split-main` | the first pane: the list. It scrolls with the page |
| `split-side` | the second pane: the thing you opened. It sticks and scrolls on its own |
| `dash` | a dashboard: a wide block beside a narrower one |
| `dash-main` | the main block of a dashboard |
| `dash-side` | the narrower block: summaries, counts, links |
| `panel` | one titled block of a dashboard or a page (its heading sits flush at the top) |
| `measure` | text that is read rather than scanned keeps one comfortable width, however wide the screen is |

A list beside a detail pane is the commonest case, and it is two class names:

```js
const main = h('div', { class: 'split-main' });   // your list
const side = h('div', { class: 'split-side' });   // what the person opened
renderList(main);
renderDetail(side, item);
el.append(h('div', { class: 'split' }, main, side));
```

On a phone this stacks with the detail under the list, which is not what you want — so ask `ctx.wide()` first, and
only build the split when it is true. That is what `jobs` does, and it is why the Jobs screen is a board on a big
screen, a list on a phone, and the list beside the open job in between.

**You can always change the kit.** It sits in the `desk.layout` cascade layer, which is the lowest priority there
is, and CSS that is not in a layer beats CSS that is. So writing `.my-list { grid-template-columns: ... }` in your
feature's own `css` overrides `cols` as normal. Never reach for `!important`.

**Cards that react to their own width.** Put `container-type: inline-size` on a card, then use `@container` instead
of `@media`, and the card adapts to how many columns there are rather than to the window:

```js
css: `
  .my-card { container-type: inline-size; }
  @container (max-width: 22rem) { .my-card button { font-size: .78rem; } }
`
```

This is how a row of cards keeps a five-button control readable whether there are two cards across or four.

When you check your work, use a wide size: `uv run tools/screens.py --sizes wide --only <screen>`. A layout can look
tidy at 1280 and still waste half a real desktop.

## 5. Rules

1. **Talk to the app only through `ctx`.** No globals of your own, no reaching into another feature's DOM, no calling
   another feature.
2. **Read anything; write only your own types and your own `ext`.**
3. **Never** use `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`, `fetch`,
   `XMLHttpRequest`, `import()`, `localStorage` or timers that run forever. The store and `net` do the storage and
   network work. The self-test scans every loaded feature's source for these words and fails the feature if it finds
   one.
4. **Pure logic goes in `logic`**, and `mount` only does the DOM work. Checks test `logic`.
5. **Plain-word strings** go in `strings`.
6. **Missing is fine.** Guard soft uses with `ctx.has('id')`. If a feature listed in `list.js` fails to load, the
   shell shows a stub with its `name` and `purpose` (taken from `Desk.planned` or the list) and the line "This part is
   not built yet." The rest of the app works normally.
7. **Registering is idempotent.** Registering the same id twice replaces the first and logs a warning.
8. **One file.** No other files except `checks/<id>.check.js` and `docs/features/<id>.md`.

## 6. Checks

```js
// checks/sites.check.js
Desk.check('sites', (t, f) => {          // f = the registered feature
  t.ok(f.logic.sortSites([]).length === 0, 'an empty list stays empty');
  t.eq(f.logic.sortSites([{name:'b'},{name:'a'}])[0].name, 'a', 'sites sort by name');
});
```

- `t.ok(condition, message)` and `t.eq(actual, expected, message)`. `t.eq` compares plain data deeply.
- Test the functions in `logic`. They are pure, so no page is needed.
- Run one check: `node checks/run.js <id>` (needs Node). On a Mac with no Node: `bash checks/check.sh <id>`, which
  uses the built-in `osascript` (this script arrives with task T1.6, so it may not exist yet). It prints
  `PASS`/`FAIL` lines and a summary. If the id is not plain a-z and hyphens, or the file is missing, it prints a
  `STOP:` sentence.
- The app's own self-test page (`#selftest`, also T1.6) runs the same checks for every loaded feature.
- **Having no check file is not a broken feature.** On `#selftest` its row says "No check file" and is not red, and
  the contract scan still runs over it. A feature built from a kit has no check file, because a kit asks for one file
  and only one. So there are two levels: `#selftest` tells you the file follows the rules, and a check file tells you
  the logic is right. Without Node, or without writing one, you check the second by using the feature.

## 7. How the contract is enforced

- **`AGENTS.md`** is the primary rule. For most agents most of the time it is enough.
- **The self-test** catches what slips through, wherever the app runs and whoever wrote the code. It scans each
  feature's source for the banned words in rule 3.
- **In a workshop folder,** edits under `features/` and `checks/` are pre-approved. Edits to `core/`, `locale/` and
  `data/` ask first. Core may need a fix nobody expected, so the person can still say yes, but "I am about to change
  the app's core" is a visible moment.

## 8. A complete example

This feature keeps short notes. It uses every part of the contract. Its source is `docs/example-feature.js` and its
check is `docs/example-feature.check.js`; the copies below are identical to those files. Run it with:

```
node checks/run.js example
```

`checks/run.js` uses the two files in `docs/` when the id is `example`. For any other id it uses `features/<id>.js`
and `checks/<id>.check.js`. You can also pass paths: `node checks/run.js <id> <featureFile> <checkFile>`.

### The feature

```js
// features/example.js  (a complete example feature: short notes)
Desk.register({
  id: 'example',
  name: 'Notes',
  purpose: 'Keep short notes about your job search.',
  types: ['note'],
  strings: {
    tabLabel: 'Notes',
    heading: 'Your notes',
    titleLabel: 'Title',
    textLabel: 'Note',
    add: 'Add note',
    remove: 'Remove',
    removed: 'Note removed.',
    added: 'Note added.',
    empty: 'No notes yet. Add your first one above.',
    needTitle: 'Please give your note a title.',
    searchLabel: 'Find a note',
  },
  css: `
    .example-form { display: grid; gap: 0.5rem; margin-bottom: 1rem; }
    .example-list { list-style: none; padding: 0; margin: 0; display: grid; gap: 0.75rem; }
    .example-note { padding: 0.75rem; border: 1px solid currentColor; border-radius: 0.5rem; }
    .example-problem { font-weight: bold; }
  `,
  logic: {
    // Newest first. Notes with the same time are put in title order.
    sortNotes(notes) {
      return notes.slice().sort((a, b) => {
        if (a.updated !== b.updated) return a.updated < b.updated ? 1 : -1;
        return String(a.title).localeCompare(String(b.title));
      });
    },
    // Tidy what the person typed. Returns { ok: true, note } or { ok: false, problem },
    // where problem is a string key for ctx.t().
    cleanNote(input) {
      const title = String(input.title || '').trim();
      const text = String(input.text || '').trim();
      if (!title) return { ok: false, problem: 'needTitle' };
      return { ok: true, note: { type: 'note', title: title, text: text } };
    },
    // Notes whose title or text contains the words typed, ignoring capital letters.
    findNotes(notes, query) {
      const q = String(query || '').trim().toLowerCase();
      if (!q) return notes;
      return notes.filter((n) => (n.title + ' ' + n.text).toLowerCase().indexOf(q) !== -1);
    },
  },
  mount(ctx) {
    const h = ctx.h;
    const logic = this.logic;
    ctx.slot('tab', {
      id: 'example',
      label: ctx.t('tabLabel'),
      order: 90,
      render(el) {
        let query = '';

  t.eq(L.findNotes(notes, 'route').map((n) => n.title), ['Bus'], 'find looks in the text too');

});
```

Things to copy from it:

- `logic` holds the thinking (sorting, tidying, finding). It has no DOM, no `Desk`, no clock.
- `logic` returns a string key for a problem (`needTitle`), and `mount` turns it into words with `ctx.t`.
- Every word a person sees is in `strings`, in plain short words.
- All elements come from `h()`. Text goes in as children, never as HTML.
- Only the `note` type is written, because that is the only type in `types`.
- Changes that touch records go through `ctx.store`, and removal is one `batch` so it can be undone.

    .example-form { display: grid; gap: 0.5rem; margin-bottom: 1rem; }
    .example-list { list-style: none; padding: 0; margin: 0; display: grid; gap: 0.75rem; }
    .example-note { padding: 0.75rem; border: 1px solid currentColor; border-radius: 0.5rem; }
    .example-problem { font-weight: bold; }
  `,
  logic: {
    // Newest first. Notes with the same time are put in title order.
    sortNotes(notes) {
      return notes.slice().sort((a, b) => {
        if (a.updated !== b.updated) return a.updated < b.updated ? 1 : -1;
        return String(a.title).localeCompare(String(b.title));
      });
    },
    // Tidy what the person typed. Returns { ok: true, note } or { ok: false, problem },
    // where problem is a string key for ctx.t().
    cleanNote(input) {
      const title = String(input.title || '').trim();
      const text = String(input.text || '').trim();
      if (!title) return { ok: false, problem: 'needTitle' };
      return { ok: true, note: { type: 'note', title: title, text: text } };
    },
    // Notes whose title or text contains the words typed, ignoring capital letters.
    findNotes(notes, query) {
      const q = String(query || '').trim().toLowerCase();
      if (!q) return notes;
      return notes.filter((n) => (n.title + ' ' + n.text).toLowerCase().indexOf(q) !== -1);
    },
  },
  mount(ctx) {
    const h = ctx.h;
    const logic = this.logic;
    ctx.slot('tab', {

      label: ctx.t('tabLabel'),

        const problem = h('p', { class: 'example-problem', role: 'alert' });
        const title = h('input', { type: 'text', id: 'example-title' });
        const text = h('textarea', { id: 'example-text', rows: '3' });
        const list = h('ul', { class: 'example-list' });

        function draw() {
          const notes = logic.findNotes(logic.sortNotes(ctx.store.all('note')), query);
          list.textContent = '';
          if (notes.length === 0) list.append(h('li', {}, ctx.t('empty')));
          notes.forEach((n) => {
            list.append(h('li', { class: 'example-note' },
              h('strong', {}, n.title),
              h('p', {}, n.text),
              h('button', { type: 'button', on: { click: () => {
                ctx.store.batch('Remove note', () => ctx.store.remove(n.id));
                ctx.ui.toast(ctx.t('removed'));
                draw();
              } } }, ctx.t('remove'))));
          });
        }

        el.append(
          h('h2', {}, ctx.t('heading')),
          h('form', { class: 'example-form', on: { submit: (e) => {
            e.preventDefault();
            const result = logic.cleanNote({ title: title.value, text: text.value });

# My examples  (id: stories, size: M)
In plain words: Short stories from your work, ready for interview questions; the coach recipe can include them.
Why someone wants it: Interviewers ask for examples ("Tell me about a time..."). It is much easier to answer when you
wrote a few down in advance.

Done when:
- [ ] An agent in the folder adds `checks/stories.check.js`, and `node checks/run.js stories` passes.
- [ ] A "My examples" item is in the menu. It lists the stories, newest first, with a title and the first line.
- [ ] You can add, edit and delete a story. A title and some text are needed. Delete can be undone with the toast's Undo.
- [ ] The form shows a small guide: "What was going on? What did you do? What happened?" (three plain prompts, as
      help text above the box).
- [ ] Text is limited to 800 characters, with a count shown. Over the limit is refused with a plain sentence.
- [ ] A warning line reminds the person: "If you share this with an AI, it goes with your question." and that names of
      other people should be left out.
- [ ] With `recipe-coach` loaded, stories are included in the practice question automatically. This already works:
      `features/recipe-coach.js` reads `ctx.store.all('story')` and uses each record's `text`. Check that a story you

Data: owns `story` = `{title, text}`. The coach reads `text` (it also accepts `story`, `body`, `what`; write `text`).
Record types: `story`.
Slots: `tab`   Soft uses: `recipe-coach` reads the `story` type by itself; this feature does not call it and does not

ctx calls: `ctx.slot('tab', ...)`, `ctx.store.all('story')`, `put`, `remove`, `batch`, `ctx.ui.toast`, `ctx.t`, `ctx.h`.

Out of scope: writing the story for the person; tags; a story picker per job.
